# Заметки по Admin API Keitaro

Всё, что пришлось выяснить об Admin API, чтобы AdRobot работал надёжно. Большая часть добыта живыми запросами к тестовому трекеру до написания кода. Эти же наблюдения зашиты в эмулятор `tests/fake_keitaro.py`, на котором идут автотесты.

Источник каждого утверждения помечен:

| Метка | Что значит |
|---|---|
| **живьём** | Проверено запросом к настоящему трекеру |
| **спека** | Взято из официальной OpenAPI-спецификации Admin API |
| **дока** | Взято из официальной документации Keitaro |

Живые проверки шли на одном трекере и одной версии Keitaro, с ключом ограниченных прав. На другой версии детали могут отличаться. Поэтому AdRobot после каждой записи сверяет ответ с отправленным и не полагается на код 200.

Базовый адрес: `https://tracker.example.com/admin_api/v1`. Номера в примерах условные.

## Авторизация и права

- Ключ передаётся заголовком `Api-Key: <ключ>`. **живьём**
- Документация допускает и `Authorization: Bearer <ключ>`. AdRobot этим вариантом не пользуется. **дока**
- Неверный ключ даёт 401 с телом `{"error": "..."}`. **живьём**
- Ключ наследует права своего пользователя. Следствие: часть справочников приходит урезанной, и ошибкой это не выглядит. `GET /domains` у ограниченного ключа вернул пустой список `[]`. Ключу были видны не все офферы трекера. Закрытые разделы отвечали телом `{"error": "You have no permission to access this page to ...", "stacktrace": null}`. **живьём**
- Код 402 по спецификации означает, что Admin API недоступен в этой редакции трекера. Живьём он не встречался. **спека** Сообщение AdRobot называет обе возможные причины: лицензия не оплачена либо в этой редакции API не предусмотрено.

Что сделано в AdRobot. Пустой или запрещённый список доменов включает режим скрытых доменов: домен определяется по существующим кампаниям либо берётся из настроек (`app/services/dictionaries.py`). Оффер, которого ключ не видит, остаётся в потоке строкой «Оффер #N» и публикуется как есть. Его можно убрать и вернуть из архива: раз привязка уже бывала в трекере, оффер существует. Добавить новый невидимый оффер нельзя, потому что проверить его существование нечем.

## Cloudflare и User-Agent

Перед трекером может стоять Cloudflare. Запрос со стандартным User-Agent библиотеки `urllib` из Python он блокирует: приходит ответ 403 с ошибкой 1010. **живьём**

```json
{"title": "Error 1010: Access denied", "status": 403, "error_code": 1010,
 "error_name": "browser_signature_banned", "cloudflare_error": true}
```

Достаточно прислать собственный User-Agent. Клиент AdRobot всегда шлёт `AdRobot-Keitaro/1.0`, значение меняется переменной `KEITARO_USER_AGENT`. Блокировку он узнаёт по полю `cloudflare_error` и объясняет, что делать: сменить User-Agent или добавить IP сервера в список разрешённых.

## Форматы ошибок

Ошибки приходят в разных видах. Клиент, который ждёт только JSON, упадёт на первом же 404.

| Код | Когда | Тело | Источник |
|---|---|---|---|
| 401 | Ключ неверный или отозван | JSON `{"error": "..."}` | живьём |
| 402 | Admin API недоступен: лицензия не оплачена либо в этой редакции трекера API не предусмотрено | JSON `{"error": "..."}` | спека |
| 403 | Нет прав у пользователя ключа | JSON `{"error": "You have no permission ...", "stacktrace": null}` | живьём тело, код по спеке не описан |
| 403 | Блокировка Cloudflare | JSON с полем `cloudflare_error` | живьём |
| 404 | Объекта нет | Простой текст, например `Traffic\Model\Campaign #1001 not found` | живьём |
| 422 | Трекер отверг данные | JSON по полям: `{"alias": ["Alias has already used"]}` | живьём |
| 406 | Не пройдены обязательные поля | JSON по полям | спека |
| 429 | Слишком часто | Не описано | не встречался |
| 5xx | Сбой трекера или прокси перед ним | Что угодно | спека |
| 200 | Несуществующий путь API | HTML-страница админки | живьём |
| 3xx | Перед нами не трекер: страница входа или прокси. Admin API не перенаправляет | Любое | не встречался |

Строка про код 200 самая коварная. Опечатка в адресе трекера или в пути даёт код 200 и HTML. Клиент считает не-JSON ошибкой при любом коде и советует проверить `KEITARO_BASE_URL`. Частая причина такой ошибки: адрес скопирован из строки браузера вместе с `/admin/#!/campaigns/15`. Настройка отрезает этот хвост сама.

Текст ошибки трекера AdRobot показывает пользователю и пишет в журнал. Прокси или отладочная страница перед трекером могут вернуть в теле заголовки запроса вместе с ключом. Поэтому клиент вырезает ключ из текста и деталей каждой ошибки до того, как она уйдёт дальше.

Как это разложено в `app/keitaro/client.py`, метод `_error_from_response`:

| Ответ трекера | Исключение | Код в ответе AdRobot |
|---|---|---|
| 401 | `KeitaroAuthError` | `keitaro_unauthorized` |
| 402, 403, Cloudflare | `KeitaroForbiddenError` | `keitaro_forbidden` |
| 404 | `KeitaroNotFoundError` | `keitaro_not_found` |
| 400, 406, 422 | `KeitaroValidationError`, словарь по полям в `details` | `keitaro_validation` |
| 429 | `KeitaroRateLimitError` | `keitaro_rate_limited` |
| 5xx | `KeitaroServerError` | `keitaro_server_error` |
| Таймаут, обрыв, DNS | `KeitaroNetworkError` | `keitaro_unreachable` |
| Не JSON, JSON не той формы, ответ 3xx | `KeitaroProtocolError` | `keitaro_bad_response` |

## Кампании

### Создание: `POST /campaigns`

```json
{
  "name": "Spring AU",
  "alias": "k3Tq9ZpL",
  "type": "position",
  "state": "active",
  "cost_type": "CPC",
  "cost_auto": true,
  "uniqueness_method": "ip_ua",
  "cookies_ttl": 24,
  "domain_id": 1,
  "group_id": 2,
  "traffic_source_id": 3,
  "parameters": {"creative_id": {"name": "utm_creative", "placeholder": "{{ad.name}}"}}
}
```

- **`alias` обязателен и уникален.** Без него приходит 422 `{"alias": ["Alias is required"]}`, с занятым приходит 422 `{"alias": ["Alias has already used"]}`. **живьём** Админка генерирует alias сама, API этого не делает. Делать alias из названия опасно: кириллица даст пустую строку, повтор названия даст конфликт. AdRobot генерирует восемь случайных символов из латиницы и цифр и при совпадении берёт другие.
- **Параметры источника не копируются.** В админке кампания получает параметры выбранного источника (utm, sub_id) автоматически. Через API поле `parameters` остаётся пустым, пока его не прислать. **живьём** AdRobot читает параметры источника из `GET /traffic_sources` и кладёт их в кампанию. Без этого ссылка кампании не содержит меток, и статистика по ним не собирается.
- **Существование домена, группы и источника не проверяется.** Любой номер принимается. Если `group_id` или `traffic_source_id` не передать, в кампании окажется 0, ошибки не будет. **живьём** AdRobot сверяет номера со справочниками до отправки.
- **Умолчания API отличаются от привычных в админке.** Без явных значений получаются `cost_auto: false` и `uniqueness_method: "ip"`. **живьём** AdRobot передаёт `cost_auto: true` и `ip_ua`, как у кампании из ТЗ.
- В ответе приходят `id`, переданные поля и `token` кампании. Поле `domain` у ограниченного ключа равно `null`, адрес домена из ответа не получить. **живьём** `token` является секретом Click API. AdRobot его не сохраняет и не показывает.
- Тип `position` означает ротацию потоков по позиции: обычные потоки проверяются сверху вниз. Поэтому поток с фильтром по стране должен стоять первым. **дока**

### Список: `GET /campaigns`

- Поддерживает `limit` и `offset`. Это единственный список с постраничной выдачей. **спека**
- Клиент читает страницами по 500, пока страница полная, и убирает дубли по `id`. Если трекер проигнорирует `limit` и отдаст всё сразу, хватит одного запроса. Страница, которая не принесла ни одной новой кампании, останавливает обход: значит, трекер игнорирует и `offset`, дальше пошли бы те же строки.
- В выдаче только кампании, доступные ключу. Проверка «название уже занято» видит только их.

### Удаление: `DELETE /campaigns/{id}`

Удаление в Keitaro означает перенос в архив. Кампанию можно восстановить из админки. По документации архив хранится ограниченное время, по умолчанию 60 дней. **дока** Повторное удаление может ответить 404. Метод `archive_campaign` считает такой ответ успехом: цель уже достигнута.

AdRobot использует удаление в двух местах: как компенсацию, когда кампания создалась, а поток нет, и для кнопки «Кампанию в архив».

## Потоки

### Чтение

`GET /campaigns/{id}/streams` отдаёт потоки вместе с вложенными `offers`, `filters` и `landings`. Для Fetch хватает одного запроса на кампанию. **живьём** `GET /streams/{id}` отдаёт один поток в том же виде. Он нужен перед Push для проверки конфликта.

У объекта потока нет надёжной отметки времени изменения. Оффер, удалённый из потока, следа не оставляет. **живьём** Поэтому конфликт ищется сравнением содержимого, а не дат.

### Создание: `POST /streams`

Первый поток, страна ведёт на редирект:

```json
{
  "campaign_id": 1001,
  "type": "regular",
  "name": "Flow 1",
  "position": 1,
  "schema": "redirect",
  "action_type": "http",
  "action_payload": "https://google.com",
  "state": "active",
  "collect_clicks": true,
  "filter_or": false,
  "weight": 100,
  "filters": [{"name": "country", "mode": "accept", "payload": ["AU"]}]
}
```

Второй поток, остальные идут на офферы:

```json
{
  "campaign_id": 1001,
  "type": "regular",
  "name": "Flow 2",
  "position": 2,
  "schema": "landings",
  "action_type": "http",
  "state": "active",
  "collect_clicks": true,
  "filter_or": false,
  "weight": 100,
  "offers": [{"offer_id": 101, "share": 100, "state": "active"}]
}
```

- **`schema`** принимает три значения: `landings`, `redirect`, `action`. **спека** Поток «только офферы» записывается как `landings` с пустым списком лендингов. Отдельного значения для офферов нет. **живьём** AdRobot считает редактируемыми только потоки `landings`.
- **`action_type` обязателен даже для `landings`**, хотя там не используется. Обязательны ещё `campaign_id`, `schema`, `type`, `name`. **спека**
- **`collect_clicks` нужно передавать явно.** По спецификации умолчание API равно `false`, и тогда поток не пишет клики в статистику. В админке флажок включён по умолчанию. **спека, дока**
- Адрес редиректа кладётся в `action_payload`.
- **Фильтр по стране:** `{"name": "country", "mode": "accept", "payload": ["AU"]}`. Коды alpha-2 заглавными, `payload` всегда список. Режимы: `accept` и `reject`. **живьём, спека**
- **Коды стран не проверяются.** Трекер сохранит `UK`, `ZZ` и любую другую строку. Ошибки не будет, фильтр просто никогда не сработает: геобаза отдаёт Великобританию как `GB`. **живьём** Справочника стран в API нет. AdRobot держит свой список из 249 кодов с алиасами: `UK` превращается в `GB`, `EL` в `GR`, названия на русском и английском распознаются (`app/keitaro/countries.py`).

## Офферы потока

Это главный запрос редактора: `PUT /streams/{id}`.

```json
{"offers": [
  {"offer_id": 101, "share": 37, "state": "active"},
  {"offer_id": 102, "share": 25, "state": "active"},
  {"offer_id": 103, "share": 38, "state": "active"}
]}
```

| Наблюдение | Источник | Что из этого следует |
|---|---|---|
| `PUT` частичный: обновляются только присланные поля | живьём, дока | Шлём одно поле `offers`. Фильтры, лендинги, название и позиция не трогаются |
| Массив `offers` заменяет набор целиком. Кого нет в массиве, тот исчезает из потока | живьём | Remove означает «не прислать оффер». Архив удалённых живёт только у нас |
| ID привязки присылать не нужно. Привязка к тому же `offer_id` сохраняет свой `id` и `created_at` | живьём | Ключ привязки у нас составляют поток и оффер, а не ID привязки |
| После Remove, Push, Bring back и Push оффер получает новую привязку с новым ID | видно в видео из ТЗ | ID привязки мы храним для справки, логика на него не опирается |
| Дубль `offer_id` в массиве молча схлопывается в одну привязку | живьём | Дубль отклоняем сами: код `offer_already_in_stream` |
| Сумма долей не проверяется: 50 и 120 сохраняются без ошибки | живьём | Сумму 100 держим сами, иначе Push закрыт. Активный оффер с долей 0 тоже считаем проблемой |
| Несуществующий `offer_id` принимается без ошибки | живьём | Оффер сверяется со справочником при Add, Bring back и перед Push |
| `state` оффера в потоке принимает `active` или `disabled` | спека | Выключенный в админке оффер передаём обратно как есть и в расчёт долей не берём |
| Порядок в массиве сохраняется, новые привязки встают в конец | видно в видео из ТЗ | Шлём офферы в порядке активации. Новый и возвращённый оказываются последними, как в оригинале |
| При удалении оффера в админке доли остальных не пересчитываются: показывается «В сумме 75%» и ссылка «Уравнять» | видно в видео из ТЗ | Fetch зеркалит такие доли как есть и показывает предупреждение |
| Доли офферов в потоке задаются вручную, автоматической оптимизации по статистике у потока нет | дока | Советник долей в AdRobot только подсказывает. Публикует по-прежнему человек |

Ответ на `PUT` содержит поток целиком с сохранённым набором офферов. AdRobot сравнивает его с отправленным. Расхождение даёт код `push_mismatch`, черновик остаётся неопубликованным.

Привязка в ответе выглядит так:

```json
{"id": 900001, "stream_id": 5002, "offer_id": 102, "state": "active", "share": 25,
 "created_at": "2026-01-01 10:00:00", "updated_at": "2026-01-01 10:05:00"}
```

## Чего Keitaro не проверяет

Сводка для тех, кто пишет свою интеграцию. Всё перечисленное трекер принимает с кодом 200.

| Что принимается молча | Чем это кончается | Где проверяет AdRobot |
|---|---|---|
| Несуществующий или архивный оффер в потоке | Часть трафика уходит в никуда | `DictionaryService.ensure_offers_usable` |
| Несуществующие группа, источник, домен в кампании | Кампания без группы, без меток, с нерабочей ссылкой | `CampaignCreator.build_plans` |
| Любая строка вместо кода страны | Фильтр никогда не срабатывает | `parse_geo_input` |
| Сумма долей не 100 | Распределение трафика не то, что на экране | `weights.check_distribution` |
| Дубль оффера в потоке | Одна привязка вместо двух | `editor.add_offer` |
| Пустой набор офферов | Трафику некуда идти | `editor.push` требует явный `allow_empty` |

## Справочники

- `GET /offers` отдаёт все офферы разом, без поиска и страниц. **спека** Поэтому AdRobot кэширует справочник в таблице `offers` и ищет по ней.
- У оффера поле `country` содержит названия стран (`["Romania"]`), хотя спецификация обещает коды. **живьём** AdRobot показывает поле как есть и не сверяет его с гео кампании.
- `GET /groups` требует параметр `type`: `campaigns`, `offers`, `landings` или `domains`. **спека, живьём**
- `GET /traffic_sources` отдаёт источники вместе с `parameters`. Оттуда AdRobot берёт параметры для кампании. **живьём**
- `GET /domains` у ограниченного ключа пуст, о чём сказано выше.

Самый лёгкий запрос для проверки связи и ключа: `GET /groups?type=campaigns`. Им пользуется `/api/health`.

## Отчёты: `POST /report/build`

Метод работает с ключом тестового трекера. **живьём** AdRobot делает два запроса на кампанию, тела взяты из `app/services/stats.py`. Период задаётся явными датами: для семи дней это сегодня и шесть дней до него.

Итоги по парам поток и оффер, колонка Stats:

```json
{
  "range": {"from": "2026-01-01", "to": "2026-01-07", "timezone": "UTC"},
  "dimensions": ["stream_id", "offer_id"],
  "measures": ["clicks", "campaign_unique_clicks", "conversions", "revenue", "cr", "epc"],
  "filters": [{"name": "campaign_id", "operator": "EQUALS", "expression": 1001}]
}
```

Клики по дням, колонка Trends:

```json
{
  "range": {"from": "2026-01-01", "to": "2026-01-07", "timezone": "UTC"},
  "dimensions": ["day", "stream_id", "offer_id"],
  "measures": ["clicks", "conversions"],
  "filters": [{"name": "campaign_id", "operator": "EQUALS", "expression": 1001}]
}
```

Ответ: `{"rows": [{...}], "total": N}`. Каждая строка содержит запрошенные измерения и метрики.

- В современной схеме поля называются `dimensions` и `measures`. В старых примерах встречаются `grouping` и `metrics`: это прежний диалект. **спека**
- У `range` два способа задать период: пресет `interval` (`today`, `yesterday`, `7_days_ago`, `1_month_ago`, `all_time` и другие) либо явные даты `from` и `to`. **спека** AdRobot пресетами не пользуется. Пресет вида `7_days_ago` захватывает лишний день, и итог по офферу перестаёт сходиться с суммой тренда по дням. С явными датами итог и тренд считаются по одному и тому же окну.
- Периоды интерфейса: `today` даёт один день, `7d` даёт семь, `30d` даёт тридцать, считая сегодня. Незнакомое значение `period` заменяется на `7d`.
- Оффер без кликов в отчёт не попадает. Отсутствие строки означает ноль, интерфейс пишет «нет кликов».
- Формат значения `day` не документирован. AdRobot берёт первые десять символов и ждёт там дату вида `2026-01-01`.
- Числа могут прийти строками. Всё приводится через `float` с запасным значением 0. Значения `nan` и `inf` тоже становятся нулём: `float` принимает их молча, а дальше на них падает `int` и их нельзя передать в JSON.
- Отчёт выполняет тяжёлый запрос на том же сервере, который обрабатывает клики. Интерфейс запрашивает статистику при открытии редактора и при смене периода. Автообновления нет.
- Это чтение методом `POST`. Клиент повторяет его как идемпотентный запрос.
- Пользователю ключа отчёты могут быть закрыты. Любая ошибка отчёта превращается в `available: false`, в колонках появляется прочерк, редактор работает дальше.
- Те же два отчёта питают советника долей. Ему нужны `clicks`, `conversions` и `revenue` по каждой паре поток и оффер. При закрытых отчётах советник отвечает, что статистика недоступна.

## Время

Даты в ответах (`created_at`, `updated_at`) приходят строкой вида `2026-01-01 10:00:00` без указания пояса. **живьём** AdRobot на них не опирается: ни в логике, ни при поиске конфликтов.

В отчётах пояс передаётся явно: `"timezone": "UTC"`. Иначе границы суток зависели бы от настроек трекера или пользователя. Дни для тренда тоже считаются в UTC. Собственные отметки AdRobot (журнал, снимки, время синхронизации) хранятся в UTC, интерфейс показывает их в поясе браузера.

## Лимиты и повторы

Ограничения на частоту запросов в документации не описаны. Трекер стоит на своём сервере, предел задают его ресурсы и прокси перед ним. **дока**

Политика клиента:

- одновременно не больше четырёх запросов (`KEITARO_MAX_CONCURRENCY`);
- таймаут 20 секунд, на установку соединения не больше 10;
- `GET`, `PUT` и `DELETE` повторяются до трёх раз при обрыве связи и ответах 429, 502, 503, 504. Пауза растёт вдвое и учитывает `Retry-After`;
- `POST` на создание не повторяется никогда. После таймаута или обрыва на чтении ответа неизвестно, создалась ли сущность, повтор наплодил бы дубли. Сообщение об ошибке просит проверить трекер. При отказе в соединении такого предупреждения нет: запрос до трекера не дошёл;
- повтор `PUT /streams/{id}` безопасен: тот же набор офферов даёт тот же результат. Это закреплено тестом, где связь рвётся уже после выполнения запроса;
- редиректам клиент не следует, а ответ 3xx считает ошибкой протокола, даже на `DELETE` и `PUT` с пустым телом.
